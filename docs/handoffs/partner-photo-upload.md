# Partner photo upload

- `CompanyProfileHero` has a separate camera button at the avatar's bottom-right; avatar and cover still support viewing. All photo-edit buttons, including the image viewer's edit button, open `pickProfileImage` even when a photo exists.
- `CompanyPhotoDialog` previews the selected local image. Existing `imageBody` validation enforces JPG/PNG/WebP <=5MB; no upload occurs before Confirm. Cancel leaves persisted photos unchanged.
- Confirm calls existing `/images` multipart upload and validates the returned Cloudinary URL through `imageService`, then calls `companyService.saveProfile` (`PUT /profile/partner`, full current organization fields, returns `AuthAccount`). `updateProfile` retains its existing save-and-refetch behavior for other callers.
- Photo saves use the response immediately: update profile URL and `authStore`, so the header avatar refreshes without navigation or additional GET dependencies. AuthAccount now types the already-existing optional avatar/cover fields from the backend response.
- Busy state/ref blocks repeated confirmation and close; unmount aborts the request. Upload/DB errors remain in the preview. A DB retry reuses the uploaded URL; choosing another image clears that cache. Shared student crop/portrait processing is unchanged.
- Verification: `node tests/partner-photo-upload-browser-check.cjs` uses isolated Cloudinary/profile API fixtures and covers cancel/no early upload, upload-before-write order, retained organization fields, immediate profile/header update, busy guard, failed upload/no DB write, failed DB save/retry without re-upload, reload and 320/1440px previews. Existing partner profile/community browser checks and `npx tsc --noEmit` also pass. No real external uploads or DB writes were used in these checks.
