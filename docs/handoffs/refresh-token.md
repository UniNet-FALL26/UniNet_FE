# Refresh token repair

- Root cause: FE discarded login refreshToken, authService.refreshToken was a placeholder, apiRequest treated every 401 as bad credentials, restoreSession could replace a rotated access token with its old snapshot.
- Existing backend contract reused: POST `/api/auth/refresh`, JSON `{ refreshToken }`, response accessToken/refreshToken/expiresAt/account. No new route, package or database migration.
- `storage.ts` retains the rotating pair/account together in memory, emits session changes to auth.store and uses generation + expected-session guards to prevent stale refresh/clear operations replacing another login. Cached profile updates preserve session identity.
- `api.ts` shares one refresh promise per session, reuses tokens already rotated by another request, validates refreshed account identity, sends no access bearer on refresh, preserves request method/body/headers and retries once. Failed login/register/google, unrelated custom bearer, anonymous 401 and 403 do not refresh.
- Refresh 400/401/403 or repeated authenticated 401 expires the original session and updates auth UI. Network/5xx/malformed response does not overwrite valid tokens. Request aborts remain aborts. Old pending refresh cannot restore logged-out state or replay a write using a different login.
- `auth.service.ts` refreshToken now calls the real endpoint. `auth.store.ts` stores both tokens, reads the current rotated access token on restore, preserves cached identity on temporary failures, and prevents late restore responses overwriting a new login.
- Backend AuthService.Refresh wraps one-use revocation and replacement issuance in a transaction. Regression test reproduces failed issuance consuming the old token before the fix and confirms rollback preserves it after the fix. Existing rotation/revocation checks retained.
- Verification: FE regression tests cover concurrent/delayed 401, token rotation, terminal/transient errors, one retry, login exclusion, logout/new-login races, manual refresh, late restore and cached identity; TypeScript and web build pass. Browser fixture: protected profile 401 -> one refresh -> successful retry, profile remains signed in, no console warnings/errors.
- Scope: tokens still use existing process-memory storage. Restart/reload still requires login; persistent Android sessions need encrypted native storage as separate work. Logout service remains its pre-existing placeholder; this repair guards local clear against pending refresh but does not introduce server logout revocation.
- No live credentials used. Authenticated physical Android expiration was not tested; frontend protocol behavior tested with mocked fetch/browser fixtures, backend rotation with SQLite. Backend transactional change is local source and needs deployment for Render to use it.
